# Dynamic coordination foundation

## Accepted V1 resolution

The bounded Fable-Sol review closed with Fable review complete, no Opus
selection, `OPEN_GAPS NONE`, and an empty flag list. Its accepted V1 decisions
are:

- preserve the existing lifecycle, comparison, result, correction-verdict, and
  decision-verdict vocabularies as the only compatibility surface;
- use strict observation and prediction schemas with mandatory causal
  attribution and explicit self-generated-evidence permission;
- select evidence deterministically by committed sequence and fail closed on
  missing, malformed, low-confidence, unsupported, or unavailable input;
- make `REBASE_REQUIRED` evaluator-exclusive and require an independently
  authorized atomic baseline plus complete prediction-set replacement;
- separate correction-verdict recording from containment exit;
- keep recurrence-derived amendment candidates read-only and non-authoritative;
- keep replay deterministic, isolated, report-only, and unable to reach
  operational completion;
- retain raw content outside controller records; controller storage holds only
  closed metadata, identifiers, hashes, lengths, and redacted values;
- preserve legacy behavior without inferred defaults and require explicit
  authority for version activation.

Status: design draft for Claude review. This document does not activate new
authority or change the standing execution rules.

## Purpose

Extend the Claude-Codex lane from a sequence of static reports into a
time-aware, feedback-driven control system. The extension must preserve the
existing role split:

- Claude owns design, interpretation, review, and proposed rule changes.
- Codex observes and acts inside a complete execution contract.
- Paul authorizes commits, merges, paid operations, external effects, and
  durable protocol amendments.

The implementation must use neutral operational language.

## Research basis and limits

Paper A (Charalambous and Djebbara, 2023, DOI
`10.1016/j.neubiorev.2023.105438`) argues that an environment should be
measured as related signals changing over time rather than reduced to a static
snapshot. Its useful systems distinctions are:

- merely tracking repeated events is different from actually matching their
  cadence;
- a disruptive event can require a timing reset rather than continuation;
- coordination can be partial and tolerance-bounded rather than exact;
- signals at different time scales can affect one another;
- active sampling switches between exploration under novelty and focused
  tracking under predictability;
- stable structure and changing trajectories jointly determine the signal an
  agent receives;
- confidence determines which unexpected observations should alter the current
  prediction.

Paper B (Paolo, Gonzalez-Billandon, and Kegl, 2024, arXiv
`2402.03824v4`) proposes four required components for an interactive agent:
observation, action, memory, and improvement. Its useful engineering
requirements are:

- act, observe the consequence, and update the local state model;
- distinguish immediate stabilizing actions from planned goal-directed work;
- separate working, episode, durable-reference, and procedural memory;
- account for data generated by the agent's own actions;
- represent uncertainty and request help when novelty exceeds competence;
- use simulation before consequential deployment while measuring the
  simulation-to-live gap;
- define the intended scope of generalization instead of claiming it vaguely;
- keep human oversight and communication rules inside the development loop.

These papers motivate systems-design hypotheses. They do not establish that a
software workflow is equivalent to the systems studied in either paper.

## Existing framework strengths

The current lane already has:

- a five-field execution contract;
- predicted observable effects for planned steps;
- readiness verification;
- bounded immediate containment;
- separate correction and decision verdict vocabularies;
- verified increments;
- a structured duplicate-aware event ledger;
- review and user gates;
- a bounded Fable-Sol retry route;
- runtime validation for contracts, readiness, reports, verdicts, and state
  transitions.

The extension should reuse these pieces rather than introduce a second
coordination protocol.

## Gaps to fill

1. Observations have no canonical runtime schema.
2. Predictions and observations are described in prose but are not compared by
   a deterministic evaluator.
3. The ledger records events but has no sequence or cadence model.
4. A major observation has no first-class `REBASE_REQUIRED` result.
5. The framework does not distinguish exploration from focused tracking.
6. Uncertainty is reported informally rather than carried as structured data.
7. Working, episode, durable-reference, and procedural memory are not
   separated.
8. The framework has no shadow simulation or replay contract.
9. It does not record how an action changes future observations or introduces
   feedback bias.
10. Generalization scope is not part of the completion contract.
11. Repeated-trigger detection stops at reporting; it does not produce a
    structured amendment candidate for Claude and Paul.

## Proposed runtime model

### Observation

```json
{
  "observation_id": "obs-0001",
  "run_id": "run-id",
  "sequence": 1,
  "observed_at": "UTC timestamp",
  "source": "tool, file, process, service, or reviewer",
  "kind": "exit_code | file_state | process_state | response | drift | metric",
  "subject": "stable identifier",
  "value": {},
  "confidence": 0.0,
  "noise": 0.0,
  "caused_by_action_id": "action-id or null",
  "content_sha256": "hash or null"
}
```

Rules:

- `sequence` is strictly increasing inside one run.
- Confidence and noise are each within `[0, 1]`.
- Content-bearing values are hashed or redacted before ledger storage.
- An observation names its source and subject; "it changed" is invalid.
- When an action may have caused the observation, preserve that link.

### Prediction

```json
{
  "prediction_id": "pred-0001",
  "step_id": "step-1",
  "subject": "stable identifier",
  "expected": {},
  "comparison": "equals | contains | exists | absent | range | changed | unchanged",
  "tolerance": {},
  "deadline_sequence": 2,
  "confidence": 0.0
}
```

Predictions remain Claude-owned design. Codex may report that a prediction is
not testable, but may not invent a replacement.

### Reconciliation result

The evaluator returns exactly one result:

- `MATCH`: observation satisfies the prediction.
- `BOUNDED_DRIFT`: difference stays within the declared tolerance.
- `DIVERGENCE`: difference exceeds tolerance.
- `UNKNOWN`: evidence is missing, too noisy, or not comparable.
- `REBASE_REQUIRED`: a disruptive observation invalidates the remaining
  sequence or baseline.

`MATCH` and `BOUNDED_DRIFT` may continue when the contract permits.
`DIVERGENCE` and `UNKNOWN` produce a `DECISION REQUEST`.
`REBASE_REQUIRED` stops the current sequence. Claude must issue a new baseline
and revised predictions before work resumes.

### Cadence profile

```json
{
  "mode": "EXPLORE | TRACK",
  "target_interval_seconds": 0.0,
  "jitter_tolerance_seconds": 0.0,
  "window_size": 1,
  "rebase_after_consecutive_divergences": 1,
  "max_observation_age_seconds": 0.0
}
```

- `TRACK` is for predictable, contract-covered sequences.
- `EXPLORE` increases sampling breadth after novelty, drift, or stale evidence.
- Cadence measures event timing; it never authorizes faster or broader action.
- A stale observation cannot satisfy a current prediction.
- Timing alignment is advisory unless the contract makes it an acceptance
  criterion.

### Action record

```json
{
  "action_id": "action-0001",
  "step_id": "step-1",
  "mode": "IMMEDIATE_CONTAINMENT | PLANNED",
  "command_or_operation": "sanitized description",
  "started_at": "UTC timestamp",
  "completed_at": "UTC timestamp or null",
  "reversal": "exact procedure or authorized-irreversible marker",
  "expected_prediction_ids": ["pred-0001"],
  "future_observation_effect": "none | selection | mutation | unknown"
}
```

Every action records whether it can alter the evidence sampled later.
`IMMEDIATE_CONTAINMENT` inherits all current narrow limits and report rules.

### Uncertainty register

```json
{
  "item_id": "unc-0001",
  "claim": "what is uncertain",
  "confidence": 0.0,
  "consequence": "what could go wrong",
  "resolution": "observation or user decision needed",
  "must_pause_below": 0.0
}
```

Low confidence does not automatically stop harmless read-only observation.
It stops any action whose consequence exceeds the contract's declared risk
tolerance.

### Memory scopes

| Scope | Contents | Lifetime | Amendment authority |
|---|---|---:|---|
| Working | Current contract, plan, predictions, latest observations | One run | Claude |
| Episode | Ordered actions, observations, reconciliations, verdicts | Durable ledger | Append-only runtime |
| Durable reference | Ratified rules, known failure patterns, verified capabilities | Cross-run | Paul |
| Procedure | Validators, transition rules, command adapters | Versioned code | Paul |

Episode records may propose but never directly change durable reference or
procedure.

### Amendment candidate

When a stable trigger recurs at least twice, the ledger may produce:

```json
{
  "trigger_key": "stable-key",
  "occurrences": 2,
  "evidence_event_ids": [1, 9],
  "affected_contract_field": "field name",
  "proposed_change": "draft only",
  "expected_benefit": "testable prediction",
  "regression_risk": "named risk",
  "status": "CANDIDATE"
}
```

Claude reviews and revises this candidate. Paul alone can ratify it. Runtime
code must never self-amend.

### Simulation and replay

A `SimulationContract` names:

- the exact scenario or episode to replay;
- the initial state;
- allowed simulated actions;
- expected observations;
- random seed when randomness exists;
- success and failure metrics;
- known differences from the live environment;
- maximum acceptable simulation-to-live gap.

Simulation output cannot prove live safety. It can reject a design, expose an
unknown, or justify a narrowly scoped live check.

### Generalization scope

Every completion contract states one level:

- `EXACT_CONTEXT`: same repository, tools, permissions, and state class.
- `RELATED_CONTEXT`: named variations with equivalent invariants.
- `UNSEEN_CONTEXT`: no prior evidence; mandatory exploration and user-visible
  uncertainty.

Claims must not exceed the tested level.

## State model extension

```text
SPECIFIED
  -> OBSERVING
  -> READY
  -> SIMULATING (optional)
  -> EXECUTING
  -> RECONCILING
       -> EXECUTING            on MATCH or permitted BOUNDED_DRIFT
       -> AWAITING_DECISION    on DIVERGENCE or UNKNOWN
       -> AWAITING_REBASE      on REBASE_REQUIRED
  -> REVIEW
  -> COMPLETE
```

Immediate containment may move `EXECUTING`, `OBSERVING`, `SIMULATING`, or
`RECONCILING` to `AWAITING_CORRECTION_VERDICT`. No other shortcut is added.

## Multi-scale loops

The same event model operates at four time scales:

1. Operation: one command or service call.
2. Increment: one smallest useful change plus its verification.
3. Task: contract through review.
4. Cross-task: recurrence, amendment candidate, and user ratification.

Higher-scale rules constrain lower-scale execution. Lower-scale evidence may
inform higher-scale revision only through the defined gates.

## Safety invariants

- No new authority is inferred from cadence, confidence, or a successful
  simulation.
- Content-bearing observations are hashed or redacted in the ledger.
- An observation never counts as independent evidence when it was generated by
  the action under evaluation unless the contract explicitly models that link.
- A disruptive event invalidates dependent predictions until Claude rebases
  them.
- Unknown and stale evidence never count as success.
- Runtime improvement produces candidates, not automatic rule changes.
- External effects, paid calls, commit, merge, and durable protocol changes
  remain user-gated.

## Implementation slices

### Slice 1: types and deterministic reconciliation

- Add observation, prediction, reconciliation, cadence, action, uncertainty,
  memory-scope, simulation, generalization, and amendment-candidate types.
- Add strict mapping validators.
- Add deterministic comparison operators and tolerance handling.
- Add sequence, freshness, confidence, and causal-link validation.

### Slice 2: ledger evolution

- Add schema versioning and migrations.
- Record sequence and causal action links.
- Query ordered episodes.
- Generate amendment candidates only from non-informational repeated triggers.
- Preserve existing redaction and concurrent insert behavior.

### Slice 3: state and orchestration

- Add `OBSERVING`, `SIMULATING`, `RECONCILING`, and `AWAITING_REBASE`.
- Bind reconciliation results to allowed transitions.
- Add exploration/tracking mode changes without expanding authority.

### Slice 4: shadow simulation

- Replay recorded episodes using deterministic fixtures.
- Compare simulated predictions with recorded observations.
- Report the declared simulation-to-live gap.

### Slice 5: protocol and command surface

- Extend the canonical protocol with the new runtime vocabulary.
- Add CLI commands for validation, reconciliation, episode display,
  amendment-candidate generation, and replay.
- Keep the canonical dispatch preamble concise; put detailed schemas in this
  reference.

## Acceptance criteria for implementation

1. Existing 25 focused tests remain green.
2. New tests cover every mapping validator and comparison operator.
3. Out-of-order sequence, stale evidence, invalid confidence, and absent causal
   links fail closed.
4. Reconciliation returns exactly the declared five-result vocabulary.
5. State transitions enforce decision and rebase pauses.
6. Ledger migration preserves existing events.
7. Stored controller payloads contain no prompt, output, note, message, or
   evidence text.
8. Informational events cannot generate amendment candidates.
9. Replay is deterministic for a fixed episode and seed.
10. Simulation output cannot transition directly to `COMPLETE`.
11. Generalization claims cannot exceed the contract's tested scope.
12. The canonical dispatch protocol retains neutral operational vocabulary.
13. Kernel tests and full audit remain clean.

## Questions for Claude

Claude should improve this design before implementation, concentrating on:

1. Which fields are essential for the first release and which should wait?
2. Should `REBASE_REQUIRED` be a reconciliation result, a state transition
   trigger, or both?
3. Which comparison operators can remain deterministic and safe without
   becoming a general expression language?
4. How should freshness and cadence defaults avoid false precision?
5. What is the smallest useful simulation/replay slice?
6. Should amendment candidates be stored in the ledger or generated as a
   derived view?
7. Which causal links are mandatory to prevent self-generated evidence from
   being mistaken for independent verification?
8. How should this integrate with the existing Fable-Sol retry history without
   duplicating its attempt records?
