## Automatic identity reconciliation

The separate `run_identity_reconciliation_loop` function runs continuously in the sidecar. `IdentityWebIndex.enqueue_people` walks the identity/routing person inventory, grouping name variants for lookup and prioritizing possible duplicates; source-only catalog records do not automatically enter this resolver. A durable SQLite queue at `audits/staffer_live_runtime/identity_reference_v1.sqlite` retains progress across restarts. Likely duplicate name families are prioritized, and route endpoints receive a persistent priority boost. Changed source fingerprints trigger new checks; temporary failures retry with exponential backoff, and completed lookups are revisited after 30 days. Site access rules, request timeouts and download limits apply. Search results provide discovery links only; snippets never prove identity.

The evidence resolver automatically consolidates compatible names when verified records establish a shared unique identity, a distinctive covered-position history, or dated office/title overlap without an ambiguous cohort. A subject-specific official biography can bridge separate career histories. For other public biographies, two independently hosted references must each corroborate the same career transition; copies and common publishers count only once. Shared names or employers alone do not qualify. Contradictory names, suffixes, birth dates, saved separations and unsupported transitive matches block a merge. Missing evidence remains unresolved rather than being described as a confirmed duplicate.

Web requests and graph rebuilding run off-request. A replacement graph is built independently and swapped only after completion, so the last valid map, searches and paths remain available. Profile additions trigger another reconciliation pass. Every consolidated person retains source IDs, source histories and reference provenance. Automatic decisions are separate from explicit user confirmations and are reproducible from the raw records and reference cache. The current resolution receipt is `audits/staffer_live_runtime/identity_resolution_receipt.json`; the live page reports actual queue and consolidation progress. Canonical source artifacts and crawler checkpoints are unchanged.

## Remaining ambiguous identities

Identity review lists possible duplicates that the automatic resolver cannot yet establish. Normalized names retrieve candidates; professional history and source references provide evidence. Cross-source candidate counts depend on the current inventory, cached references and saved decisions. Kathleen's original match remains explicitly user-confirmed.

The person panel offers pairwise **Combine** and **Keep separate** actions. Combine requires an explicit confirmation for the selected pair and applies a consistent alias mapping to search, profile evidence and introduction routes. Keep separate saves the rejected pair and suppresses that pair from subsequent suggestions while leaving other plausible pairs available. Decisions are checked against existing confirmations to prevent alias cycles or contradictory separation rules. Explicit confirmation can join records from different sources, including Politico and payroll; matching names alone cannot.

`POST /api/staffer-identity` accepts `primary_id`, `alias_ids` and `decision` (`merge` or `keep_separate`). The service validates that the records are known people in the displayed review group. The review helper atomically writes the assertion file beside the **served** Python module, normally `<source-root>/fec/surfaces/staffer_user_assertions.json`. Rebuilding the dashboard overlay retains source records, dates, provenance and the original model weights. The page reports reindexing while the identity-dependent view is rebuilt. A saved decision is not a raw-source or canonical identity promotion.

Staffer (`objective=work_time`) uses Dijkstra search over payroll and directory work exposure. `work_sources=directory` is the explicit comparison mode; `payroll_and_directory` is the Staffer default. Detailed dated directory/payroll rows take precedence over trajectory summaries. Trajectories fill uncovered intervals. The index clips exposure to the routing as-of date, retains original future end bounds, and does not infer work before a supplied start. Admin employment is excluded and internship rows can contribute to observed headcount without creating work edges.

Each shared-workplace exposure integrates the product of both people's concurrent-job allocations divided by observed peer headcount, with a workplace-type multiplier. Recognized shared-employee titles have factors 0.02 in the House, 0.05 in the Senate, and 0.02 when chamber is unknown; these are assumptions. Saturating strength and a 0.8 per-hop factor produce structural route costs. Uncertainty adds costs for unverified present access, age, and workplace concentration. Separate overlap runs contribute recency in proportion to their exposure; a brief return does not refresh a long old overlap. Source evidence and modeled-window labels are restricted to the actual joint intervals. Same-name records are not merged by routing. Member context affects office terminal anchors only, with a 15% maximum bonus; it does not rank person-to-person routes.

Ecosystem (`objective=evidence_cost`) uses separate association costs and bidirectional Dijkstra. Neither model estimates friendship or willingness. There is no wall-clock or expansion cutoff on route searches, although neighborhood browsing has paging and effort limits. Unknown people, insufficient work coverage, pending searches and exhausted connectivity remain distinct states.

General LDA routes use the sealed sparse SQLite index at `<source-root>/audits/staffer_live_runtime/lda_activity_v1.sqlite` with its sibling `.sqlite.receipt.json`. It contains all 1,037,547 activities and 2,741,465 exact `NAMED_ON_ACTIVITY` incidences for all 25,340 LDA IDs, without generating all person pairs. ## Route choices

The path finder defaults to up to three distinct introduction chains. Choose Best route only, Up to 3 routes, or Up to 5 routes, then select a result to update the map, contact, and hop evidence. Both Staffer and Ecosystem networks support person and office destinations. Office routes stop at the first eligible staff contact. Changing endpoints, network, count, or evidence revision clears the previous choices.

The route APIs accept `route_count` (integer 1–5; default 1 for API clients). Multiple-route responses retain the best route at the top level and add `routes`, `routes_requested`, and `routes_returned`. `alternative_strategy=distinct` greedily skips intermediaries from earlier choices, including same-displayed-name records for exclusion only. `independent` also skips earlier recorded workplace/organization contexts; missing context cannot prove independence. Each route is best under its accumulated exclusions; the portfolio is not globally optimized. Fewer results do not prove that no larger disjoint portfolio exists. `ranked` uses Yen loopless alternatives and may reuse intermediaries.

`avoid_people` is empty by default. Active exclusions are visible in the toolbar, form and result list, with per-person removal and clear-all controls. Saved links retain explicit exclusions and display them on restoration. Clear and Reset view remove them. Alternative-specific skips are named alongside their selected route; they do not become a permanent blacklist.

The current implementation is governed by `staffer_work_sources.py`, `staffer_closeness_routes.py`, `staffer_distinct_routes.py`, `staffer_routing.py`, and `fec/staffer_network/{closeness_math,relationship_uncertainty,member_context}.py`. The map and exclusion controls live in the adjacent JavaScript files. Static historical member rankings are a separate artifact and are not rebuilt by payroll promotion.
