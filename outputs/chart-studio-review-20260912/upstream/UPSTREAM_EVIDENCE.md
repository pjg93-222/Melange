## Confirmed using published data and the current chart engine

1. **The Banking Spending Overview can triple-count its cycle money.** In the Banking workbook, `Spending Overview!C21` is the 2023–2024 Total Giving value, $26,107,204.16. Rows 22–25 divide that same total by contributor role; rows 26–35 divide it by recipient category. The actual `chart-math.js` engine, configured Cycle / SUM(Total Giving), sums C21:C35 to **$78,321,612.48**. Filtering Scope=Total Giving returns **$26,107,204.16**. Across all three cycles, unrestricted marks total $164,288,532.15 versus $54,762,844.05 for Total Giving rows. This proves chart aggregation inflation relative to the workbook's existing included basis, not that the underlying included basis is independently correct.

2. **Splitting semicolon ZIP cells repeats dollars.** Banking `Employee List!F6:F4505` contains 4,500 displayed cycle-person amounts totaling **$36,925,530.61**, paired with ZIP strings in `O6:O4505`. They are top-150-per-company rows, 1,500 per cycle for 2021–2022, 2023–2024, 2025–2026, and are not the complete Banking contribution universe. With the actual engine's SUM and `splitMulti=false`, marks sum to $36,925,530.61. With `splitMulti=true`, 2,229 cells split, 7,333 rows result, and marks sum to **$89,135,413.84** (+$52,209,883.23). Both runs use maxGroups=60 and include the Other mark, so this is not truncation. The engine emits a warning but allows the inflation. `chart-math.js:88–119` explicitly replicates full measures for each semicolon part. `crypto_workbook_builder.mjs:356` limits the displayed employee group subset to 150 per company/cycle; `:1749` exports concatenated employee ZIPs. Concatenated ZIPs are person history, not contribution-level geographic allocation.

3. **Raw Amount can reintroduce already-excluded copies.** Crypto `2023-2024!H24:H28` contains five $23,000,000 Coinbase/Fairshake observations from the same filed contribution date: raw sum **$115,000,000**. `I24:I28` (Analysis Amount) sums to **$23,000,000**; four rows are already excluded as exact five-key memo duplicates. This is an existing working protection in included money, not an uncorrected $92m overstatement in that particular included total. A chart selecting Amount instead of Analysis Amount revives those excluded observations.

4. **Industry and Company views overlap, including the exact prior validation figure.** Banking `Recipient List!N6:N9998` has 9,993 rows. The actual chart engine returns **$109,525,688.10** with no View filter. Industry view has 3,342 rows and sums to **$54,762,844.05**; Company view has 6,651 rows and sums to the same **$54,762,844.05**. Their combination is exactly double, to cents, across the three cycles. The attached fields report's cited unchanged $109,525,688.10 therefore preserves an already-overlapping sum; it establishes arithmetic preservation, not a valid giving total. Receipts: `banking_recipient_reconciliation.json`, `recipient_math_reproduction.json`, with reproducible extracted inputs in `banking_recipient_chart_data.json`. Crypto Recipient List has the same structural overlap: for 2023–2024, Industry and Company views each independently sum to **$145,462,078.45**; combining them doubles it. The same equality holds in the other two Crypto cycles.

Reproduction receipts: `chart_math_reproduction.json`, `reproduce_chart_math.cjs`, `banking_employee_chart_data.json`, `banking_overview_chart_data.json`. Extracted input values and row numbers came from authoritative workbooks; Python and the pure engine were run with no writes to those workbooks.

## Upstream accounting basis confirmed in code

- `R/report.R:2064–2071` merges contributions and corporate_giving, favors accepted rows, and deduplicates on `sub_id`. `:1521–1544` guards against repeated or blank kept sub_ids and kept exact memo duplicates. These protect source-row uniqueness.
- `R/collect.R:103–113` defines countability using accepted match, no exclusion reason, no exact memo duplicate, and allowed receipt role. It does **not** filter superseded amendments or duplicate filing versions. `R/report.R:3117` says so explicitly.
- `tests/test_report.R:273–305` intentionally expects an original $100 observation and its $125 amendment to total $225, while flagging the original superseded. `:455–501` expects five $23m filing-version observations to remain as five rows in its fixture. `:142–166` expects conduit, earmark and memo records for different displayed recipients all to count.
- Hence current receipt-as-shown totals are not guaranteed unique economic contributions. The cited tests are code semantics, not proof of live dollar corrections.
- Crypto published 2023–2024 data contains **169 included rows flagged Duplicate Filing Version totaling $65,140,793.73**, plus **one included Superseded Amendment row totaling $1,000**. These figures quantify rows requiring transaction/evidence reconciliation. They are **not a validated amount to subtract**: flags can overlap source and memo decisions, and must be assessed with amendment links and receipt roles.
- The current code excludes recognized asset-liquidation and other-receipt roles (`R/collect.R:25–113`); the July Crypto workbook is not proof that those newer rules have been deployed. No corrected all-industry total was established in this review.
- Direct contributions, committee transfers, downstream candidate activity, and attributed estimates need separate money measures. The published Crypto `Beneficiary Bridge!A2` expressly says company associations repeat committee activity and are not attributed company dollars. `R6:R9` repeats $305 of associated Bakkt funding alongside different WinRed downstream candidate paths. `Downstream Activity!A2` states same-cycle committee activity is not dollar-level pass-through attribution.

Official FEC data documentation explains that TRAN_ID can persist through the original report and multiple amendments, whereas SUB_ID identifies a row. Memo X can represent earmarking, partnership detail or previously reported activity, so blanket removal of all memo rows is also incorrect. Source: https://www.fec.gov/campaign-finance-data/contributions-individuals-file-description/ (accessed 2026-09-12). Conduit reporting source: https://www.fec.gov/help-candidates-and-committees/filing-reports/contributions-received-through-conduits/.

## ZIP availability and publication gap

- Source collectors retain `contributor_zip`, `contributor_city`, `contributor_state`, amount, date, source IDs and committee IDs (`R/collect.R:3–23`, `:1175`). The full exporter retains ZIP/state/city (`tools/export_crypto_spending_data.R:499–550`).
- `R/report.R:1781–1990` builds fine-grain Contributor Detail and Recipient Detail, restricted to included observations. ZIP5 is text, normalized from the first five characters; invalid/missing ZIP stays a blank bucket. The default 45,000-row cap folds low-valued groups into Other by company/cycle, preserving totals but losing those groups' geographic detail. This makes a reconciled total, not complete mappable coverage.
- `tools/export_crypto_spending_data.R:864–874` carries detail as separate payload keys so raw-row compaction cannot remove them. `R/export_guards.R:468–511` reconciles those detail totals against cycle totals.
- **None of the eight authoritative published workbooks currently contains Contributor Detail or Recipient Detail.** The new export code is not yet present in those files. Inventory is in `published_inventory.json`.
- Crypto, Community Banks, Credit Union and Fintech have full A:AI cycle sheets including ZIP. Banking and Telecom cycle sheets are A:L aggregate facts. Credit Arms and Property & Casualty Insurance are A:R compact facts. Banking/Telecom therefore cannot recover contribution ZIP attribution from those cycle sheets alone.
- `app/report_insights.py:245–296` loads every nonempty worksheet row (including totals/subsections), infers general type, and returns saved formula results; no semantic grain or measure additivity contract exists in the reader. It refuses sheets exceeding 50,000 rows. Banking Downstream Activity has 135,111 sheet rows and Telecom 99,355, so those sheets exceed the current reader ceiling.
- Contributor ZIP geography and candidate district geography are different concepts. Existing beneficiary State/District is the candidate's office geography; it does not assign a donor's ZIP to a district.

## Implementation implications

Prioritize a semantic contribution dataset with named accounting basis and one contribution/event key; safe money measures should filter inclusion automatically, preserve refunds and record lineage, and prevent mixing raw facts, summaries and reused transfer context. Let charts choose one analytical view and grain. For ZIP maps use transaction ZIP5 and valid geometry, retaining unmapped and folded totals explicitly. Do not distribute a person's full cycle giving to every ZIP in their history; do not treat candidate district as donor district. Verification must conserve money across filters/groupings/layers and reconcile approved event-level sums separately from workbook subtotal arithmetic.
