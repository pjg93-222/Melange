# Independent review of the two console findings

Reviewed the root audit's `reproduce_console.py` and `console-reproductions.json`, the current console launch/stop implementation, resilient runner, workbook build lock and Excel finalization mutex. No real collection processes were launched or killed.

**Keep — P2: launch exclusion is local to one Console instance.** [server.py:294](C:/Users/pgoff/Mentat/mentat/app/server.py:294) creates a separate `threading.Lock()` for each Console. The manifest/active-process checks at [389–410, link to 389](C:/Users/pgoff/Mentat/mentat/app/server.py:389) therefore do not serialize two writable consoles sharing the same root. The reproduction's barriers simply arrange for both instances to finish the checks before either commits `state=preparing`; both legitimately return `starting` and invoke the mocked preparation. This is a feasible ordering, not a bypass of the actual predicate.

Downstream controls reduce the damage but do not eliminate it. Resilient runner [line 638](C:/Users/pgoff/Mentat/mentat/tools/parallel/Start-MentatResilientIndustryReports.ps1:638) creates a distinct timestamp/PID run directory for each accepted launcher, including separate collection databases at line 670. There is no global collection exclusion between those launchers. The [workbook lock at line 627](C:/Users/pgoff/Mentat/mentat/tools/build_industry_report.ps1:627) and [Excel mutex at line 243](C:/Users/pgoff/Mentat/mentat/tools/finalize_crypto_excel.ps1:243) serialize later workbook work; they cannot undo duplicate runtime copying, API collection or compute already performed. Both launches also use the same upload's [launcher.log and upload.pid at server.py:491–499](C:/Users/pgoff/Mentat/mentat/app/server.py:491), compromising run ownership/status even though separate collection databases and shared quota reservations limit corruption/quota-overrun claims. Describe confirmed exposure as duplicate collection, wasted budget and competing upload lifecycle state; do not claim proven data corruption. Four writable consoles sharing the configured root makes the prerequisite relevant in the observed installation.

**Keep — P1: force-stop trusts a saved PID without verifying the process belongs to that run.** [server.py:543](C:/Users/pgoff/Mentat/mentat/app/server.py:543) selects an in-memory process PID or the manifest PID, and [line 551](C:/Users/pgoff/Mentat/mentat/app/server.py:551) immediately runs `taskkill /PID <pid> /T /F`. It checks neither terminal run state nor process creation identity. The offline reproduction confirms a manifest explicitly marked `completed` still attempts that command with the saved PID. After a console restart the original process handle is absent, so Windows can reuse that historical PID for an unrelated process; the endpoint would then forcibly terminate that process and its descendants. No collection or workbook lock validates this target. This is conditional exposure, not evidence an unrelated process has already been killed. Reject terminal runs and validate creation-time/owned-process identity before allowing destructive stop; checking numeric PID liveness alone would remain insufficient.
