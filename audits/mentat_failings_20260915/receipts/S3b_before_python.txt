A fourth, project-specific escaping risk this lane found the hard way while
writing the FEC-bulk fixture builder embedded as a Python script inside a JS
template literal (splice_browser_test.py's PYTHON_S3B_FIXTURE_SCRIPT): a
literal two-backslash Python string (backslash-r-backslash-n), written
directly inside a JS backtick literal, is escape-processed once by JS itself
(backslash-r/backslash-n become real CR/LF control bytes) before Python ever
sees the generated script -- breaking the emitted .py file's own string
literal ("SyntaxError: unterminated string literal"). `node --check` alone
never caught this, because it only validates the OUTER .cjs syntax, not the
Python string produced at runtime; it was only caught by actually running
the generated fixture script inside the browser test. Fixed by writing four
backslashes in the JS source (two escaped backslash-pairs), so JS's own
escaping reduces it to the intended two-character sequence by the time
Python parses it -- verified by evaluating the template literal in Node (not
regex-extracting the raw source text, which skips JS's own escape processing
entirely), py_compile-checking the result, and then actually running it and
inspecting the produced .zip/.xlsx bytes.
