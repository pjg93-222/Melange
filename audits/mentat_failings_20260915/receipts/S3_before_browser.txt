HANG FOUND AND FIXED (before the red result below could even be produced)
=======================================================================================

Two of my own early runs of this exact script against this exact pristine
worktree hung indefinitely with zero output (confirmed via
Get-CimInstance Win32_Process: real `python app/server.py` and `node
tests/test_evidence_csv_browser.cjs` processes alive for 10-20+ minutes, no
progress). This was NOT a hang in the server or in the old client - it was a
performance bug in this test's OWN fixture generator:

    function buildCsvOfSize(targetBytes) {
      let text = HEADER;
      let index = 1;
      while (Buffer.byteLength(text, 'utf8') < targetBytes) {   // <-- BUG
        text += csvRow(index);
        index += 1;
      }
      return text;
    }

`Buffer.byteLength(text, 'utf8')` re-encodes the ENTIRE accumulated string on
every loop iteration. For a 40,000,000-byte target built ~530,000 rows at a
time, that is O(n^2) total work, not O(n) - confirmed in isolation with a
standalone timing script: unfixed, building six.csv+forty.csv did not finish
within a 270s external `timeout` wrapper (exit code 124, stuck forever on
"STEP 1: write fixture CSVs..."); fixed (tracking a running byte counter
instead of re-measuring the whole string), the identical two files build in
30ms + 187ms.

Fix applied (both here and in the four-column generator's call sites are
unchanged): accumulate lines in an array, track bytes with a running counter
updated by `Buffer.byteLength(row, 'utf8')` on each new (short) row only, and
`parts.join('')` once at the end. Propagated to both
C:\Users\pgoff\Mentat\mentat\tests\test_evidence_csv_browser.cjs (live tree)
and this scratch worktree's copy; `node --check` passed on both after the
edit, and a `grep`/`cmp` byte-diff confirmed the regex/unicode content
(the `\d`, `\.`, en dash U+2013, and middle-dot U+00B7 characters used in the
exact-status-text assertions) survived the edit unmangled.

Separately hardened while investigating (defense in depth, not required to
fix the actual bug, but left in since a red-team run should not be able to
hang silently again): a top-level 240s watchdog that force-exits and names
the last-started step if anything ever blocks past that bound, and a
`console.log('STEP N: ...')` printed at the START of every step (previously
only a `PASS step N` was printed at the END, so a genuine hang gave zero
diagnostic output - exactly what happened above).

Two hung Node process trees from the pre-fix attempts were killed by PID+tree
(`taskkill /F /T /PID <pid>`) rather than by name, and confirmed via a
Win32_Process query for `mentat-evidence`/`test_evidence_csv_browser` in the
command line that nothing else was affected - no port-8802/8806/8808 console
and no other lane's process was touched.
