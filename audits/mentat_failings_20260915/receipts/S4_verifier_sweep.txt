TWO CORRECTIONS TO THE SWEEP REPORT ABOVE, both load-bearing
--------------------------------------------------------------------------------
1. Section F's "HEAD commit: 91fe7402a126eca3a38deeca0f7a84402632d8dd (VERIFIED)"
   is FALSE. Commit 21c9cab6d ("Read PAC evidence from any file type and any path
   on this computer", the S3b lane) has committer date 2026-09-16 21:58:36 -0400,
   which is 8 minutes 20 seconds BEFORE this sweep's own 22:06:56 header. HEAD at
   sweep time was 21c9cab6d, not 91fe7402a. The word VERIFIED was not earned.
   This matters because 21c9cab6d is the direct cause of one of the two reds.
   Section F's "Tracked files changed: 10 files" is likewise inconsistent with the

2. This report records only the NAMES of the two red tests. It records none of
   their output, so the first failing assertion could not be read from it and had
   to be re-derived by re-running both tests. A sweep that reports a red without
   its failing tail cannot be acted on. Future sweeps must keep the tail.

The "Step 7 / browser.close() timeout" characterisation that reached the
coordinator is also wrong on both counts: the real first failure is at STEP 14,
and "browser.close() exceeded its 10000ms bound" is a line printed AFTER the
failure, on the way out of an already-failed run. It is a consequence, not a
cause, and not an assertion.

ROOT CAUSE, with file:line on both sides
--------------------------------------------------------------------------------
The test pins a message the console deliberately retired 8 minutes before the
sweep ran.

  EXPECTED by the test:
    mentat/tests/test_evidence_csv_browser.cjs:499  (working tree)
    mentat/tests/test_evidence_csv_browser.cjs:421  (same line at HEAD)
      await waitForStatusExact('latin1.csv: Use a UTF-8 CSV file without invalid text characters.');

  PRODUCED by the console:
    mentat/app/evidence_csv.py:191
      M_BINARY = 'This file contains binary data and could not be read as text.'

  And the console says in its own source, at mentat/app/evidence_csv.py:187-190,
  that the expected string is dead:
      # M_UTF8 above is kept defined for callers that still import it, but nothing
      # raises it any more: a file that is not valid UTF-8 is decoded as
      # Windows-1252 and says so in the catalog, and only content that is not text
      # at all (a NUL byte outside UTF-16) is refused, as M_BINARY.

  The fixture matches that rule exactly. latin1Buffer() at
  mentat/tests/test_evidence_csv_browser.cjs:76-83 emits the bytes
  [0xff, 0xfe, 0x00] - a NUL outside UTF-16 - so under the new reader it is
  binary, by design, and M_BINARY is the correct answer. The test, not the
  console, is what is stale.

  Provenance of the change, by search rather than by assertion:
    git log -S "binary data and could not be read as text" -- mentat/app/evidence_csv.py
      -> 21c9cab6d  Read PAC evidence from any file type and any path on this computer
  M_BINARY did not exist before 21c9cab6d. That commit is dated 21:58:36; the
  sweep ran at 22:06:56. The red was already unavoidable when the sweep started.

  21c9cab6d's own message predicted this: "The extended browser test and the
  real-client receipt follow in the next commit." The extension did land in the
  working tree at 22:16:26 (+213/-6, HARD_CAP_MS 870000 -> 1_200_000, 14 new
  steps, step 10 relabelled to "notes.txt is read as delimited text and refused
  for its header") - but it did NOT update step 14. So both the committed test
  and its uncommitted extension still pin the retired string.

WHY THIS IS NOT S4
--------------------------------------------------------------------------------
Nothing on the failing path is S4's. app/evidence_csv.py and app/evidence-csv.js
are not S4 files and appear in no S4 patch. The failing assertion reads
#evidence-csv-status in the PAC evidence tab; it never touches the contributions
session, the catalog, build_stamp, DIMENSIONS, schema_version, the stored-view
migration or the industries parse. S4's server.py hunks do not touch the
/api/evidence-csv routes.

WHY THIS IS NOT LOAD
--------------------------------------------------------------------------------
Two runs alone, 36 s apart in duration, identical failure. The status line is not
a timeout artefact: the server had already answered and the browser had already
rendered the final text. The receipt's own log shows the settled answer -
  state "failed", message "This file contains binary data and could not be read
  as text." - so the 15 s waitForFunction expired waiting for a string that will
  never arrive, however quiet the host is.

ACTION: none taken here. This is S3's test and S3's regression; the S4 lane does
not edit it. The fix is one line - update
mentat/tests/test_evidence_csv_browser.cjs:499 to the M_BINARY text, and rename
the step from "rejected for invalid UTF-8 bytes" to what the console now does -
which tightens the test to the shipped contract rather than weakening it. That
belongs to whoever closes out 21c9cab6d's deferred test work. Flagged to the
coordinator.
