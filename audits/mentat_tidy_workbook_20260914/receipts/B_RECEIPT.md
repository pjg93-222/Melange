## 3. What each patch does

- **P1 `R/tidy_stage.R` (new, 1299 lines).** `MENTAT_TIDY_TABLE_SPECS` is the contract in
  code (column order + SQLite affinity per table); it drives `dbWriteTable`'s `field.types`
  so a zero-row table still lands with the right columns and types. Coercion helpers
  (`mentat_tidy_text/id/date/money/count/flag`) enforce "" -> NULL, ISO-text dates, INTEGER
  flags and TEXT identifiers. Frame builders for contributions, giving/recipient/contributor/
  location facts, committees, committee_sponsors, candidates, downstream_activity,
  beneficiary_bridge, state_destinations, recipient_locations, data_quality and metadata.
  `mentat_build_tidy_frames()` assembles them in dependency order. `mentat_write_tidy_stage()`
  writes to `<path>.pending-<pid>` inside ONE transaction, then renames.
  `mentat_guard_tidy_reconciliation()` returns the `mentat_guard_result` shape and fails on
  either a cycle-total mismatch or a duplicated row key.

## 4. Deviations from the contract / plan, with reasons

1. **`--overview-receipt` is a path that did not exist.** The plan says to pass the
   finalizer receipt path "used at :741/:714". There is no receipt FILE: `finalize_crypto_excel.ps1:741`
   emits the object on STDOUT and `build_industry_report.ps1:816` captures it into
   `$formulaReceiptObject` (replayed from the workbook cache manifest at :714 on a cache hit).
   P5 therefore writes that object to `<stage>\formula_receipt.json` with the existing
   `Write-AtomicText` and passes THAT path. It works on both the fresh-build and cache-hit
   paths and carries the Excel-computed `cycle_totals` the writer reconciles against.
2. **The workbook cache manifest is now written twice on a fresh build, and once on a
   cache hit.** `data_workbook_sha256` cannot be known when the manifest is first written
   (:830-837), because the writer has not run yet. P5 leaves that write untouched and
   rewrites the manifest after publication. Consequence: `generated_at` in that manifest
   now changes on a cache-hit build. Nothing reads that field (checked repo-wide: only
   `app/cross-reference.js` and a studio test use a `generated_at`, both from different
   objects), and the fields the cache decision depends on are replayed verbatim.
3. **An absent `tools/build_tidy_workbook.py` WARNS and publishes the Overview only.**
   The two lanes can land in either order, and making a missing Lane A file fatal would
   break every Overview build until it lands. The skip is loud (`Write-Warning`) and visible
   in the result object (`data_workbook` is `null`). **This is an open question - see 5.1.**
4. **`funding_cohorts` drops two fields the Python side has.** The contract's 2.12 list is
   9 columns; `enrich()` also produces `funding_source_type` and `funding_direction` per
   cohort row. I emitted exactly the contract's 9 rather than silently widening a table
   Lane A's writer reads generically. **Open question - see 5.2.**
5. **`committees` classification columns come from `contributions`, not `committee_map`.**
   `recipient_category`, `category_source`, `party` and `party_source` are per-receipt
   columns; taking the modal value from the receipts guarantees the Committees sheet and the
   Contributions sheet can never disagree about the category a committee was counted under.
   `committee_map` supplies only fields that exist nowhere else. The committee NAME still
   prefers the official master spelling.
6. **`data_quality.metric` is TEXT, not REAL.** The contract's 2.13 table does not give a
   type for `metric`. Three producers write it and they disagree about what it means (a row
   count, a dollar figure, a cycle count), so a numeric column would invite a chart that
   sums them. Lane A should format it as text.
7. **`contributor_facts.distinct_addresses` is grouped by (cycle, company, person_key).**
   The contract says "for the person in that cycle (all parties)". Company is included
   because `person_key` is already company-scoped in the exporter's construction; this is a
   no-op in practice and makes the join key explicit.
8. **`beneficiary_bridge` flag columns are appended beyond the declared spec.** The token
   vocabulary is data-derived (contract 2.11 says so), so they cannot be declared up front.
   They are written as INTEGER and sorted, so two runs over the same data produce the same
   column order - verified by the byte-identical-store check.
9. **The example committee-type label in the contract's section 4 does not match the live
   code book.** The contract shows `"Super PAC (independent expenditure-only)"`; `R/report.R:1753`
   says `"Independent expenditure-only (Super PAC)"`. The contract's rows are explicitly
   synthetic, so I used the live label via `mentat_fec_code_label`. Lane A's fixtures should
   not hard-code the contract's spelling.
10. **`mentat_state_destinations(workbook_raw_export)` and the `recipient_locations`
    `unique()` are computed a second time** for the staging frames, rather than hoisting the
    payload's computation into a variable. Recomputation keeps the patch purely additive at
    the payload site. Both are O(n) single passes; on Banking this is a measurable but small
    cost, and it only happens when staging is requested.
11. **P1 bug found by its own test, worth recording:** `data.table(key = ..., value = ...)`
    silently swallows a column named `key`, because `key` is a reserved argument of
    `data.table()`. The metadata frame is now built with `as.data.table(list(...))`.
    Anything else in this repo building a `key` column with `data.table()` has the same bug.

## 5. Open questions for Paul

1. **Must a cache-hit build re-run the writer?** As drafted: yes, every build runs the
   writer, because the Data book is published from the staging store (not from the Overview)
   and the workbook cache only covers the Overview. That costs one writer run per build even
   when nothing changed. The alternative is a `data_workbook_sha256` check against the
   workbook manifest and a skip - cheaper, but it would republish an unverified file. I chose
   the safe one. **UPDATED 2026-09-15:** the second half of this question is now moot for
   the apply order. P8 puts Lane A's writer in the tree BEFORE P5 turns staging on, so
   `tools/build_tidy_workbook.py` is always present and the absent-writer warning never
   fires on a correctly applied tree. The graceful branch is kept deliberately - it is what
   makes P5 safe to apply out of order or to roll P8 back alone - but it is now dead code on
   the intended tree, and its firing is itself the signal that P8 was skipped. Whether to
   harden it into a `throw` once both lanes are committed is still yours to call.
2. **`funding_cohorts`: add `funding_source_type` and `funding_direction`?** They exist in
   `enrich()` and are dropped by the contract's column list. They look chartable.
3. **6th positional argument vs an environment variable.** I used the positional argument the
   plan specifies. An env var (`MENTAT_TIDY_STAGE`) would avoid ever having to renumber
   arguments again and would be picked up by any caller of the exporter, including ad-hoc
   console runs. The positional form is more explicit and shows up in process listings; the
   env var is harder to get wrong. Flag if you want it switched - it is a 6-line change.
4. **Should the Data book be excluded from `published_reports()` entirely** rather than
   catalogued with `kind: 'data'`? As drafted it appears in the report picker under its own
   industry. That is what makes it chartable in the Studio, which is the point, but it does
   mean two entries per industry in that list.
5. **`recipient_locations` is deduplicated on (cycle_label, committee_id).** The live payload
   key is `unique(..., by = cycle/committee_id/recipient/<6 destination fields>)`, which can
