# Independent desktop client

The current release target is Windows x64. Each app has an independent Electron identity, data directory, credential entry, backend process, and update channel. End users do not need Docker.

## Local access and visible update status

New builds default to `DESKTOP_ACCESS_MODE=standalone`. Melange and Mentat use a local password and protected device session. Terrier uses its real local Django account/password and administrator role. Opening these builds does not request remote administrator approval or contact the Bore approval endpoint. Existing verified local password/device records can migrate into separately encrypted local records; existing application data and old managed records remain available. No managed grant, bearer token or private-server permission is synthesized. The legacy managed mode remains an explicit build option.

All three apps check their own public GitHub Releases directly. The launch, local sign-in and settings screens show the installed version and update state; the main window title retains that status. A successful current check, a cached result, API cooldown, a download, a prepared update and a failed check are reported separately. A failed or deferred check never says the app is freshly synchronized. This updates published application releases, not arbitrary source commits or user files.

Update discovery starts before local sign-in or dataset preparation. A running version awaiting backend readiness can still discover a newer corrective release while retaining the last confirmed recovery baseline. A version 1.0.23 installation already stuck in its previous readiness logic may need one manual upgrade. Public dataset downloads are separate from application updates and retain their signed catalogue, hash and rollback checks; their availability does not imply private-server access.

For the optional private publisher or shared scrape broker, select `DESKTOP_ACCESS_MODE=managed` explicitly. Standalone builds refuse those private services. The packaged trust descriptor still supplies the signed GitHub verification keys; its legacy access-server URL is not used for standalone authorization.

The runtime launcher prefers `runtime/<app>/python/python.exe` with `bootstrap/desktop_backend.py`. It passes `-E -s -u`, rejects host Python fallback, and removes inherited Python path/home settings. A real bundled interpreter preserves application child-script semantics. The earlier frozen backend remains supported for development artifacts only. The native credential helper uses the same app-specific runtime.

## Building the signed Windows installer

For each app, the release driver provisions `DESKTOP_APP_ID`, the staged runtime, administrator trust descriptor, private signing root, exact signing certificate and publisher identity. From this client directory, the normal build command is:

```powershell
npm run build -- --win --x64 --publish never
```

`build-native.cjs` runs electron-builder's Windows `dir` target and signing hooks in one process, then compiles the signed program using the built-in NSIS installer with per-file zlib compression. It signs the final installer and writes its `.signatures.json` receipt, including current native-file hashes/signatures, `installerFormat: builtin-nsis-v1`, an empty `installerPlugins` list, and intentionally absent uninstaller evidence. Existing valid vendor signatures are preserved. No production unsigned fallback or external NSIS plug-in is used. The intermediate `win-unpacked` folder and `npm run build:dir` are staging outputs, not finished release delivery.

The build produces `<Product>-<version>-win-x64.exe` beside `win-unpacked`. The release driver performs its package-bound gates and signed-feed publication, using canonical GitHub names `<app>-<version>-win32-x64.exe`; it also publishes the signed manifest and trust assets. `npm run build` alone does not publish an update. See [the release procedure](../GITHUB_RELEASES.md).

The installer keeps per-file progress while avoiding thousands of details-list insertions during extraction. It preserves all program files and the initial recovery copy; no end-to-end install-time improvement has been measured. Version 1.0.23 and its stable signed feeds were published before the standalone-access changes described above; source changes alone do not upgrade that existing package. [The ThreatLocker deployment guide](THREATLOCKER-DEPLOYMENT.md) covers IT's complete-application capture workflow, shortcuts, required execution paths and the locally inspected 1.0.22 vendor signatures.

## Update lifecycle

> **Signing prerequisite.** Releases are staged and published by `packaging/release_from_main.py` (`--publish` to publish), which calls `packaging/github_release.py` for each app's own repository (see `../GITHUB_RELEASES.md`, "Release from main"). A signed release needs the approved Windows Authenticode identity and per-app update roots enrolled in the protected publisher state. The production Windows wrapper requires that signing configuration; it does not produce unsigned fallback installers.

- New builds default to public GitHub Releases with `DESKTOP_UPDATE_PROVIDER=github` and `DESKTOP_GITHUB_REPOSITORY` unset, which selects the app's own repository (Melange `pjg93-222/Melange`, Mentat `pjg93-222/Mentat`, Terrier `pjg93-222/Geo`); the variable still overrides it. The repository must be public; no GitHub token is bundled or sent. Installer metadata pins this source and the administrator-provisioned per-app verification keys. Public binary updates work while app access is pending or its server is unavailable; application login, approval and runtime authorization remain independent.
- Packaged applications include the receiver. After successful extraction, the installer registers the same installed executable with `--desktop-updater` in the current user's login-startup entry; ordinary app startup maintains that registration. Login launches the updater without starting an application backend or opening a window. Ordinary launches, network reconnects, resume, unlock, and a 15-minute timer also check for signed releases. Execution policy must permit the installed app for both foreground use and this receiver.
- GitHub discovery selects stable `desktop-v<version>` releases. Each app requires its signed `<app>-win32-x64.manifest.json`, `<app>-trust.json` transitions and `<app>-<version>-win32-x64.exe`. The manifest binds `purpose: melange-desktop-github-release`, `distribution: public-installations`, the configured repository, exact app/version/platform/architecture, source repository/ref/commit for all three apps, package hashes and a monotonic release sequence. GitHub API metadata is not an installation authority. Native activation still goes through the existing verified local feed and `electron-updater`.
- Discovery scans at most five pages of 100 releases and selects the highest matching desktop semantic version. Container `v*` releases, drafts and prereleases are ignored; GitHub's generic latest-release endpoint is never used. Keep active desktop releases within this 500-release discovery window. Current-version recovery uses its exact tag independently of that window.
- Public discovery metadata is cached per OS user and repository (so each app, having its own repository, has its own cache) under `AppData/MelangeDesktop/github-discovery`. A successful list, including an empty list, is reused for six hours plus up to 30 minutes of jitter. The 15-minute lifecycle checks reuse this cache; settings report its check time and next discovery time. Manual checks respect this same interval. SQLite serializes refreshes across app processes, releases locks on crash, and bounds competing waits to two seconds. Cached metadata is bounded and revalidated; signatures, versions, hashes and native publisher checks remain mandatory.
- GitHub 429 and quota-related 403 responses persist a shared cooldown using `Retry-After`/rate-reset headers, with a one-hour fallback plus jitter. It applies across restarts and to exact-tag API requests too; ordinary access-denied 403 errors do not become quota responses. This reduces shared-IP request pressure without embedding GitHub credentials. A fleet behind one public IP still shares GitHub's unauthenticated allowance and requires monitored rollout; no unlimited desktop count is claimed.
- GitHub uses normal HTTPS certificate authority and hostname verification. Metadata and downloads have size/time limits; API redirects are refused. Asset redirects are bounded and allowed only to GitHub's explicit asset hosts. Credentials, cookies, access tokens and device identifiers are never sent. GitHub state and recovery caches are separate from the optional publisher state.
- The optional custom publisher remains available with `DESKTOP_UPDATE_PROVIDER=publisher`. Its receiver enrollment and per-recipient release authorization follow the next two bullets; they do not gate public GitHub binary updates.
- Administrator access activation automatically enrolls that approved app/device for updates using `/v1/access/update-enrollment`. The server issues a separate download credential; it never reuses the access token. The receiver checks the returned app, device, origin, TLS pin and per-app keys against its existing protected trust, then stores the credential in the OS credential store. Lost responses and failed local saves retry the same idempotent exchange. Existing manual pairing and signed update-key history are preserved. Enrollment does not publish or authorize a release for the recipient.
- The administrator-supplied trust descriptor may name an internet HTTPS hostname or a local IPv4 HTTPS server. DNS resolves the configured name; every connection still verifies the exact pinned TLS public key and certificate validity, with SNI for DNS hosts. Redirects, userinfo, paths, queries, fragments, ambiguous IP forms, another application/platform, invalid signatures, altered bytes, older versions and older release sequences are refused. Network detection sends no discovery traffic.
- `electron-updater` is pinned to 6.8.9 and `electron-builder` to 26.15.3. The native Windows updater skips Authenticode verification when `publisherName` is absent. This client therefore refuses update preparation unless its packaged publisher identity exactly matches the native updater configuration. A locally built unsigned installer is not a distributable release.
- Packages and signed envelopes are retained independently of application binaries. The client saves transaction state before activation and rechecks hashes before invoking the native installer. It never enables `autoInstallOnAppQuit`; activation follows explicit application close or a background login session with no running backend or visible application window.
- OS shutdown suppresses activation. A staged package can be restored from its verified local cache after restart even when the administrator is offline. A previous activation that did not reach the intended version is suspended rather than retried indefinitely. A new version is reported installed only after its backend starts successfully.
- Existing renderer `beforeunload` vetoes remain active. Normal close requires confirmation to save work and finish calculations. An authenticated backend `busy: true` response prevents close. Mentat exposes its actual running-job state; unknown or unsupported signals do not claim that an application is idle. No timer force-closes a window or backend.

## Local recovery

The **Restore previous authorized version** menu prepares only the retained, previously installed package selected from local recovery state. It requires explicit local confirmation, checks its signed envelope and hashes, and passes it through native publisher verification. Program files change only after normal close. Writable data remains separate and is not deleted.

This narrow recovery exception does not reset the normal update sequence/version high-water mark. Successful recovery suspends the failed version; the administrator must publish a newer corrected release. Recovery is not a remote command or a generic downgrade interface.

Before the first upgrade, publish signed recovery metadata and the installer for the running version. GitHub resolves its exact `desktop-v<running-version>` tag; the optional publisher uses its recipient-restricted recovery endpoint and requires recipient approval. Both paths verify the seed's signed metadata (exact running version, sequence equivocation and high-water) and retain only that manifest: establishing the baseline does not download the running version's installer again. Missing or invalid seed metadata blocks activation.

An interactive first install makes a best-effort copy of its setup file to `%LOCALAPPDATA%\<application id>\baseline\<version>`, preserving the downloaded filename. Silent updates skip that extra copy. Verified update installers remain in `%LOCALAPPDATA%\<application id>\updater\updates\<sequence>`, outside the synced Documents profile; update state and high-water remain in the profile. The current and previous installers are retained, with older copies pruned after the new version is confirmed running. Installers at the old cache location are ignored and fetched again when needed. The new installer is per-user and deliberately creates no uninstaller; it makes no promise of automatic removal of these files when someone manually deletes the program folder.

Offline recovery requires the retained signed manifest and a matching local installer. The copy receives the same signed-manifest hash and pinned native-publisher checks as any activation and is staged through `<Downloads>\MelangeApplications\updates\<app>\pending\`. If the local copy is missing or invalid, recovery needs the original package to remain hosted. Retaining an extra installer per app costs the size of that release's package; removing this copy to speed up first install would weaken offline recovery. A rollback request parks any other pending update so it cannot install over the restored version.

Verified updates apply without asking: silently when the app closes, or, if one is still pending (for example after an OS shutdown), at the next start before any window or backend opens, then the app relaunches. Updates are always on and do not depend on the release certificate being in the Windows Trusted Root store: the Ed25519-signed manifest and the package sha256/sha512 hashes gate every install, and the app never asks to trust the certificate. `publisher-trust.cjs`, the bundled certificate and `turn-on-updates.cmd` are no longer used by the app. A pending update installed at launch shows an "Installing update" window; a second launch request during it is recorded and the app relaunches afterwards; if the signature tool gives no verdict three starts in a row the update installs on close instead. Accepted release high-water marks never decrease. All accepted manifests require `dataSchemaVersion: 1`; restoring program files cannot undo changes to data.

Terrier stores state and data separately for each supported district. Existing unscoped state requires explicit migration; it is not silently relocated. The desktop adapter disables passwordless local administration (`CU_LOCAL_ADMIN=0`). The approved, bound owner of an existing Terrier installation is never asked for a password: the signed native launch is the verification, there is no flag file to set, and a leftover `.desktop-password-lock-disabled` file is ignored. Other approved Terrier accounts use the existing invitation/password flow. All apps refuse data paths overlapping installed files, including junction aliases. Mentat's private PNG renderer accepts bounded HTML bytes over a separately authenticated loopback service and exposes no renderer IPC, path loading or remote command interface.

## Signing in on a computer

Melange and Mentat verify a computer once. After administrator approval the first launch asks for a local password and a sign-in with it. A successful sign-in keeps a small device record (credential namespace `access-device`, one per app and device, in the operating-system credential store) bound to the approved account and the current approval. It holds no password and no verifier. Later launches open without any prompt, including after sleep or a locked screen, which still hide the workspace.

The record never replaces administrator approval: every launch still needs the current signed approval, so a revocation, a missing approval or a replacement approval (a new grant) asks for the password again. A missing, damaged or unreadable record, or a helper without the `access-device` namespace, also falls back to the password, and a record that cannot be written never blocks sign-in. To forget a computer, choose **Lock workspace** from the app menu and then **Lock** in the access window: both the session and the record are deleted, and the next open asks for the password once more and remembers the computer again. Deleting the `MelangeSystems.Desktop.Access.Device.<app>/<device id>` entry in Windows Credential Manager also forgets it, but the running app keeps its checked result until it restarts.

Terrier's approved owner is never asked for a password, and its access window has no Lock button.

## Validation and limits

`npm test` covers transport, trust, lifecycle, recovery, network, activity, enrollment, district isolation and installed-path boundaries. A real Electron 44.7.2 smoke verified the setup renderer's sandbox, context isolation, absent Node integration, and clean close lifecycle. These results do not prove signed native installation, clean-machine deployment, full application feature parity, or migration safety. Production publishing remains gated on those separate checks and a provisioned signing identity.

## Delivering installers that receive updates from anywhere

1. Make the configured GitHub distribution repository public. Stage all three gated installers using the [GitHub release procedure](../GITHUB_RELEASES.md), including a signed current-version recovery seed, then publish the versioned release. Source commits alone do not publish installable updates. Never replace an existing release asset or reuse its sequence for different bytes.
2. Set `DESKTOP_ACCESS_TRUST` to the independently provisioned administrator trust descriptor while building each app; its per-app update keys are the GitHub verification roots. Configure the actual Windows code-signing identity and `WINDOWS_PUBLISHER_NAME`. Build a new versioned candidate and sign it. Access approval still requires its own reachable server, but GitHub binary downloads do not contact that server.
3. Install and run the signed package on a clean Windows x64 recipient. The installer registers the included receiver's background login launch; it initializes from packaged trust. Follow the [ThreatLocker deployment guide](THREATLOCKER-DEPLOYMENT.md) where company execution policy applies. App access approval controls feature access separately. A fresh installer is required to bootstrap older unsigned local testing installations.
4. Prove a signed version upgrade, offline use, interruption/restart and recovery on a second device before broad delivery. Run the existing source, dependency, native-signature and package-bound acceptance gates for the exact rebuilt bytes.

For the optional publisher transport, configure a reachable endpoint with `--public-origin`, pin its exact TLS public key in the descriptor, and expose only its recipient API. Publisher downloads require recipient authorization. No hostname, firewall opening, listener or service is provisioned by this client.

Committing source does not build, sign or publish desktop installers. The current platform tag workflow builds Linux container images and its install kit; it does not build these native Electron installers. Desktop publication and app access approval remain distinct operations. The existing 1.0.1 local-testing installers remain unchanged. Current access protection, bundled runtime and native activation support Windows x64 only; macOS/Linux need their own credential, runtime, signing and recovery implementations and acceptance before they can be offered.


Terrier district changes now keep the same native window open. The renderer shows its branded loading screen while the target local backend opens, then stays in the same section with district-specific query selections cleared. Initial foreground launch also shows the bundled Terrier animation immediately, before opening any authorized workspace. No minimum animation duration delays readiness.

The launcher keeps at most three visited district runtimes, evicting inactive runtimes when available system memory falls below 2 GiB. Each selection revalidates district data and signed access; file fingerprints invalidate retained runtimes after account, snapshot or dataset replacement. Full owner probes run asynchronously in parallel and validated mappings may be reused for two seconds only while all relevant file fingerprints remain unchanged. Explicit calculation activity and renderer beforeunload vetoes retain their protections. Lock, sleep and revocation block the workspace and remove inactive runtimes; quitting stops all owned backends.

Terrier recipients (not the existing-owner PC) receive each approved district privately from the access server: after access is activated the app downloads every approved district that is not on disk (`%LOCALAPPDATA%MelangeData	errierstoresdistricts<id>`), verifies the signed revision, unzips only the allowlisted files into staging, refuses SQLite files in WAL mode, runs the same district check as a district switch, then swaps the directory in and starts the backend. Progress shows on the loading screen; network failures retry with backoff, and an offline start with every approved district present makes no request. Their per-district state (accounts, imported snapshots, secrets) is kept in `<store>\state\districts\<id>`, beside the data and outside the Documents profile (runtime-roots.cjs; the existing owner PC and any data directory chosen by hand keep the profile state). Districts no longer approved are deleted at launch with their data and state, and learning of revocation stops the backend and deletes the whole store; program updates keep the store. Isolated test profiles use `<profile>packs` instead. See `district-packs.cjs`.

District downloads are bounded by the signed per-object rawSize (bytes after gunzip): unzipping stops at that size and refuses an object that ends short, and free space is checked per district before the download (gzip plus unzipped bytes) and before unzipping; a full disk (ENOSPC) or a locked file (EBUSY) is reported as such and keeps the downloaded cache. A tester moved from the old default profile data folder to the store has the old data/districts and state/districts folders of that profile deleted (never for the existing owner or a data directory chosen by hand; a failed removal retries at the next start). Their Chromium session data (sessionData, set before ready) and backend.log / district-data.log live in the store (session and logs folders, removed with it) instead of the Documents profile. A district bundle the backend could not import is still served; the backend leaves state/bundle-import-failed and the app shows a status until the next start imports it.

Local phase measurements are written to the selected profile's logs/district-switch.jsonl: verification, backend readiness, navigation and renderer readiness, with district ID, cache hit and monotonic elapsed milliseconds. No account credentials, launch tokens or address data are logged. Cold and warm native timings must be measured on the installed build; unit-test durations are not user-facing latency measurements.

A folder-portable Terrier package includes resources/portable-mode.json with schemaVersion 1 and appId terrier. This marker suppresses login-startup registration and native installer/update activation only; access refresh, authentication, per-user Documents state and data boundaries remain active. Replace the extracted program folder to update a portable copy. New computers still need their own access approval and separately prepared district data. Private accounts, datasets and credentials are never part of the program ZIP.
